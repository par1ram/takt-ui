# Как проверять Takt

Для работы над компонентом запускайте `bun run test`. Для полной проверки установите зависимости и браузеры Playwright, затем выполните одну команду. Каталог и тестовое приложение запускаются на свободных локальных портах и завершаются автоматически.

```sh
bun install --frozen-lockfile
bunx playwright install chromium firefox webkit
bun run test:all
```

На Linux зависимости браузеров можно установить командой `bunx playwright install --with-deps chromium firefox webkit`. Полный прогон использует сеть для установки пакетов в чистое приложение и обращения к реестру shadcn.

## Пирамида

| Уровень | Что может сломаться | Где и как проверить |
| --- | --- | --- |
| Модульный | Неверный адрес установки на preview-домене, потеря клиентской границы в примере, ошибка перевода, мутация чужой реакции | `tests/unit/` · `bun run test:unit` |
| React-компонент | Публичный экспорт перестал рендериться на сервере, исчез внешний `className`, контролируемое поле потеряло значение, отменённый запрос перезаписал результат | `tests/components/` · `bun run test:components`. SSR проходит по каталогу. Поведенческие тесты монтируют компоненты через Testing Library |
| Контракты и интеграции | Карточка агента ведёт к другому экспорту, в пакете отсутствует CSS Module, демо и установочный пример расходятся, компонент игнорирует новые пропсы или ошибку провайдера | `tests/contracts/` и `scripts/review-motion-host.mjs` · `bun run test:integration`. Контракты проверяют оба языка, Chromium проверяет реакцию на события тестового приложения и имитируемого платёжного провайдера |
| Сквозной | Агент не находит компонент по задаче, CLI устанавливает файлы по неправильному алиасу, пример не компилируется у потребителя, черновик пропадает при навигации | `tests/e2e/` · `bun run test:e2e`. Сценарии используют production-каталог, настоящий shadcn CLI и MCP. Временный Next.js-проект устанавливает обе коллекции и проверяет каждый пример через TypeScript |

После изменения исходников выполните `bun run build` до отдельного запуска интеграционных или сквозных тестов. Полный цикл включает сборку и ESLint. Для быстрой проверки уже собранных JSON подходит `bun run test:contracts`.

## Браузерные проверки

- Для каждой записи реестра требуется сценарий в `scripts/review-motion.mjs`. Набор проверяет совпадение списка сценариев и реестра, затем проходит демо в Chromium на настольном и мобильном размерах, в светлой и тёмной темах, с обычной и уменьшенной анимацией.
- `bun run test:a11y` проверяет каждое демо в его начальном состоянии через axe. Обе темы проверяются на английском и русском. Нарушение проверяемых правил WCAG 2.0/2.1 A и AA завершает тест ошибкой. JSON с компонентом, элементом и причиной сохраняется в `test-results/`. Клавиатурные переходы и возвращение фокуса дополнительно проверяются действиями в браузере. Полезность озвучивания и удобство интерфейса для человека требуют ручной проверки.
- Визуальные тесты сравнивают геометрию и цвета переключателя в четырёх сочетаниях темы и состояния. Эталоны находятся в `tests/e2e/snapshots/`. После намеренного изменения дизайна выполните `bun run test:e2e visual.pw.mjs --update-snapshots` и просмотрите изменённые PNG.
- Мессенджер проходит один пользовательский сценарий в Chromium, Firefox и WebKit. Сценарий устанавливает разные размеры экрана и проверяет отправку сообщения, переход между каналами и сохранение черновиков.

## При добавлении компонента

1. Добавьте запись в каталог и реестр. SSR, проверка двух языков, установка примеров и аудит доступности подхватят её автоматически. Если при рендере обязательны данные, задайте минимальный пользовательский пример в `tests/components/ssr.test.js`.
2. Опишите основное взаимодействие с демо в `scripts/review-motion.mjs`. Пропсы и колбэки, ошибки, повторные запросы и граничные входные данные проверяйте на самом быстром уровне, где воспроизводится поведение.
3. Если пользовательский сценарий пересекает границу приложения, проверьте его через реальный вход. Для поиска агентом это MCP, для установки — чистое приложение с собственным алиасом, для навигации — браузер.
4. Запустите `bun run test:all`. GitHub Actions выполняет те же этапы для pull request и push в main. Артефакты содержат LCOV и диагностику Playwright.

Команда `bun run test:coverage` формирует `coverage/lcov.info` и печатает покрытие строк и функций для исходников, исполненных быстрыми тестами. Контракты, дочерние процессы и действия браузеров проверяются отдельными этапами и в этот процент не входят.
